# Heka Goal Contract v0.1

目标不是一句“我想变得更好”。它是用户确认后、可被行动和现实检验的意图。

Heka 采用七个字段保存一个目标；它们来自 Leader 的目标定义方法，但不授权 Heka 自主行动。

| 字段 | 用户要确认的内容 | 在 Heka 中的作用 |
| --- | --- | --- |
| `purpose` | 为什么这个目标在此阶段重要 | 信念与目标图中的目标节点 |
| `done_state` | 什么状态出现才算完成 | 避免把忙碌当完成 |
| `proof` | 用什么事实证明完成 | 行动层与结果回写的证据标准 |
| `anti_shortcuts` | 哪些“看似完成”的方式不算 | 防止错误奖励与自我欺骗 |
| `bounds` | 时间、精力、金钱、隐私等边界 | 决策模型的硬约束 |
| `tradeoffs` | 冲突时优先保留什么 | 目标与目标之间的排序规则 |
| `unknowns` | 还没决定、需要观察的部分 | 解释层的追问来源，而不是系统擅自补全 |

## 生命周期

```text
草稿 → 用户确认 → 进行中 → 结果回写 → 复盘
                  ↘ 暂停 / 放弃（保留原因）
```

- 草稿中的任何字段都不改变个人模型。
- 目标与 Trace 的关系必须标为 `support`、`counter_evidence`、`progress` 或 `outcome`。
- “未完成”不是负面证据；只有在约定完成态和证据标准后，结果才可以解释为进展或偏离。
- 目标可以被修订，但旧版本必须可追溯。不能用新目标覆盖旧目标来伪造连续性。

## 例子

```json
{
  "title": "验证 Heka 是否能帮助我更清楚地判断机会",
  "purpose": "减少只靠即时情绪做机会判断的情况",
  "done_state": "连续四周记录至少六个机会，并能复盘其中三个选择的理由与结果",
  "proof": ["六个已确认 decision_case", "三个 outcome 回写"],
  "anti_shortcuts": ["只记录支持既有想法的机会", "把 AI 的解释当作自己的理由"],
  "bounds": ["每次记录不超过十分钟", "不上传原始日记到云端"],
  "tradeoffs": ["证据质量优先于记录数量"],
  "unknowns": ["什么样的机会才算可比较的样本"]
}
```

这个契约属于第三层“信念与目标图”，并向第五层“决策模型”、第六层“行动层”和第七层“演化模型”提供同一套验收语言。
